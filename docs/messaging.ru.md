# Сообщения

Ретранслирует с юнита **входящие SMS и входящие звонки** и **отправляет** с
него: пушит в ntfy для оповещений, отдаёт по HTTP API и по расписанию держит
SIM живой, чтобы оператор её не забрал.

Телефон собирает и складывает в спул. Всё остальное — хранение, политика
ретрансляции, ретраи, учётные данные — на хосте. Телефон не хранит секретов,
кроме им же сгенерированных, и не открывает сокетов.

> Русский перевод [messaging.md](./messaging.md). Исходная английская версия — основная.

```text
телефон                                      хост
┌───────────────────────────────┐
│ приложение-компаньон          │   adb    ┌─────────────────────┐
│   RECEIVE_SMS ──► спул входящих│◄────────►│ gateway ──► SQLite  │
│   SEND_SMS   ◄── keepalive    │  drain   │    └──────► ntfy    │
└───────────────┬───────────────┘   ack    │ api (FastAPI) ──► вы│
                │ бродкасты                └─────────────────────┘
┌───────────────┴───────────────┐
│ rackphone-companion (Magisk)  │  настройки, действия, статус, метрики
└───────────────────────────────┘
```

В Magisk-модуле нет телефонной логики. Он переводит настройки и действия
Rackphone в бродкасты и читает то, что записало приложение, — поэтому контракт
плагина (`rackphone config`, `set`, `action`, `status`, метрики) работает с
приложением ровно так же, как работал с shell-коллектором.

## Почему приложение и чего это стоило

Первая версия коллектора была shell-скриптом, который читал
`/data/data/com.android.providers.telephony/databases/mmssms.db` через
`sqlite3 -readonly` из-под root. Он работал, и у него было две проблемы,
которых у приложения нет.

**Он вообще не мог отправлять.** Поддерживаемого пути из шелла нет: у
`cmd phone` нет подкоманды отправки, а до биндера `isms` можно достучаться лишь
через `service call isms <txn>` с сырым номером транзакции, который смещается
между версиями Android, — неверная догадка вызовет другой метод сервиса
телефонии. Для отправки нужно приложение с `SEND_SMS`, а раз оно уже есть,
приём в нём же снимает и вторую проблему.

**Приём зависел от приватной схемы.** Вывод `content query` невозможно
разобрать — он печатает `col=value, col=value`, поэтому тело с `", "` неотличимо
от границы колонок, — оставалось читать базу провайдера напрямую. Эта база не
публичный API, обновление LineageOS могло её сдвинуть, и `selftest` у коллектора
существовал в основном ради этого. Приложению с `RECEIVE_SMS` система отдаёт
каждое сообщение сама, уже разобранным и по частям, и схема перестаёт быть
проблемой проекта.

Чего это стоило, стоит сказать прямо:

- **APK нужно установить и выдать ему разрешения.** И то и другое делается с
  хоста через `adb install` и `pm grant`, без единого тапа, но шаг установки у
  юнита теперь есть.
- **Звонки классифицируются грубее.** Приложение видит состояние телефона, а не
  журнал звонков: «звонит, потом тишина» — это пропущенный, и отклонённый сетью
  или чёрным списком выглядит точно так же. Оба уезжают как `missed`. На юните
  без оператора значимый факт один и тот же: кто-то позвонил и не получил
  ответа.
- **Нет добора истории.** Старый коллектор мог отдать записи, появившиеся до
  него. Приложение видит только то, что приходит, пока оно установлено.

## Доставка не менее одного раза, и это осознанно

`drain` внутри приложения отодвигает спул в файл «в полёте» и печатает его.
События удаляются только когда хост вызывает `ack`, а делает он это **после**
их фиксации. Обрыв в любой точке между этим означает, что пачка будет доставлена
повторно, а не потеряна.

Дубликат гасится ограничением `UNIQUE (unit, kind, source_id)` и
`INSERT OR IGNORE` в `store.py`, а не логикой приложения. Дальше передаются
только строки, которые действительно оказались новыми, поэтому **дедуп
хранилища является и дедупом ntfy**.

Этот размен сделан намеренно. Дублирующее уведомление — раздражение;
потерянная SMS — невидима.

Идентификатор события обязан быть целым числом и обязан расти даже после
переустановки: счётчик, начавшийся заново с 1, столкнулся бы с событиями,
которые хост сохранил месяцы назад, и выброшенным дубликатом оказалось бы
**новое** сообщение, а не старое. Приложение засевает последовательность из
часов, а они назад не идут.

## Отправка

```sh
uv run --project cli rackphone action companion keepalive   # проверить путь
```

Произвольная отправка идёт через бродкаст `SEND`, до которого хост дотягивается
по adb. `POST /api/messages` пока возвращает **501**: путь на устройстве уже
есть, а маршрут, который бы его дёргал из API, ещё не подключён.

Полный список бродкастов — в [README приложения](../app/README.md), включая
ловушку с кавычками, которая молча обрезает многословное тело.

## Keepalive

Оператор забирает SIM, которой не пользуются, а юнит в стойке только принимает —
то есть ничего из его работы за использование не считается. Приложение само, по
своему расписанию, отправляет одно сообщение — на каждую SIM.

«На каждую» важно для двух SIM: оператор видит только свою, трафик по одной
ничего не говорит о другой, и общее на устройство расписание позволило бы тихой
SIM умереть за спиной активной. Любая успешная отправка считается активностью
именно этой SIM, поэтому та, через которую хост уже что-то слал, лишнего не
отправит.

Расписание живёт на устройстве, а не в кроне хоста, потому что SIM теряется
одинаково — и когда хост выдернули, и когда его переустановили, и когда про него
просто забыли.

## Будильник, который система может не выполнить

Телефон, который никто не открывает, для Android — заброшенное приложение:
самый низкий standby-бакет и отложенные до года будильники. Keepalive,
назначенный через 28 дней, оказался назначен политикой на 364. При этом ничего
в юните не выглядело сломанным.

`task app-install` кладёт приложение в список исключений idle и в бакет
`active`, всё с хоста. Само состояние приложение докладывает, а не считает
данностью — `rackphone_companion_battery_exempt` и строка `alarms` в
`rackphone status`, — потому что система может забрать это обратно, и больше
никто бы не заметил.

## Баланс

Keepalive закрывает случай, когда SIM забирают за бездействие. Он ничего не
говорит про второй способ умереть у предоплатной карты — пустой баланс, где
первый симптом это неудавшаяся отправка через месяц после того, как это стало
важно. Поэтому приложение по расписанию читает баланс через USSD, и он ложится
рядом со всем остальным:

```sh
uv run --project cli rackphone action companion balance
```

```text
rackphone_companion_balance{sub_id="1"} 430.0
rackphone_companion_balance_age_seconds{sub_id="1"} 18
```

Возраст показания здесь не украшение: баланс, который перестали обновлять, — уже
не баланс, и алерт на одно значение замолчал бы ровно тогда, когда SIM перестала
отвечать.

## Конфигурация

Настройки устройства — через обычный контракт плагина:

| Ключ | По умолчанию | Примечания |
| --- | --- | --- |
| `companion.collect_sms` | `1` | Приходящие сообщения; отправленные не ретранслируются |
| `companion.collect_calls` | `1` | Пропущенные и отвеченные входящие |
| `companion.include_body` | `1` | Выключение отдаёт только отправителя и время |
| `companion.inbox_cap` | `2000` | Сверх этого старые отбрасываются и считаются |
| `companion.keepalive_enabled` | `0` | По умолчанию выключено: это трата денег на SIM, условия которой знаете только вы |
| `companion.keepalive_to` | `self` | Номер или собственный номер каждой SIM |
| `companion.keepalive_interval_hours` | `720` | 30 дней против 90–180, которые обычно дают операторы |
| `companion.keepalive_subs` | `all` | `all` держит обе SIM, `default` сужает до одной |
| `companion.keepalive_body` | `rackphone keepalive` | ASCII, чтобы остаться одной частью GSM-7 |
| `companion.balance_code` | `*102#` | USSD-код баланса; пустое значение выключает проверки |
| `companion.balance_interval_hours` | `24` | Каждая проверка — сетевой запрос |

`self` разрешается только если оператор записал номер на SIM, а многие не
записали. Когда он не разрешается, попытка фиксируется как `no_target`, а
`rackphone_companion_keepalive_targets{resolves="false"}` уходит выше нуля —
потому что «SIM поддерживается живой» — ровно то убеждение, которое не должно
оказаться ложным.

Настройки хоста живут **вне репозитория**, так как включают учётные данные
ntfy: `~/.config/rackphone/gateway.toml`, переопределяются по ключам через
переменные окружения `RACKPHONE_*`. `gateway.example.toml` — отслеживаемая копия,
она пустая.

```sh
uv run --project cli rackphone gwconfig   # секреты показываются как set/unset
```

Пустой `ntfy.url` — поддерживаемое состояние: события сохраняются и отдаются, и
из сети ничего не уходит.

## Запуск

```sh
uv run --project cli rackphone gateway            # цикл drain + API
```

```sh
uv run --project cli rackphone gateway --once     # один проход и выход
```

| Эндпоинт | |
| --- | --- |
| `GET /health` | Статус, счётчики событий, статистика drain |
| `GET /api/messages` | `unit`, `since`, `limit` |
| `GET /api/calls` | те же фильтры |
| `GET /api/events` | плюс `kind` |
| `GET /api/stream` | SSE обо всём, сохранённом после подключения |
| `GET /docs` | OpenAPI |

По умолчанию слушает `127.0.0.1:9106` без аутентификации. Задайте `api_token`
**до** расширения адреса — API отдаёт содержимое сообщений.

## Формат уведомлений

Тело уходит как есть, а отправитель стоит в заголовке:

```text
SMS from +79001234567
Код подтверждения: 4821
```

```text
Missed call
+79001234567
```

**Оформление — дело того, кто рисует уведомление**, и разметка, добавленная
здесь, до экрана не доезжает. Каждый потребитель экранирует тело, прежде чем
обернуть его в свой конверт: так делают клиенты ntfy, так обязан делать и мост в
Telegram — иначе SMS с `<b>` сломала бы сообщение, в которое она вставлена.
Поэтому и ``` , и `<pre>`, добавленные на этом конце, приходят просто символами.

Значит, тот, кому нужен моноширинный блок, оборачивает тело у себя — там, где
экранирование уже происходит:

```python
lines.extend(["", f"<pre>{html.escape(message)}</pre>"])
```

Вокруг тела не добавляется ничего. **Ни времени, ни длительности звонка**:
каждый клиент рисует свой конверт — время получения, приоритет, теги, — и
повторять что-то из этого внутри значит тратить те две строки, которые у пуша
вообще есть. Время события (когда его получил телефон, а не когда отправили
пуш) и длительность звонка остаются в хранилище и в API.

Номер стоит в заголовке для SMS, где тело несёт сообщение, и в теле для
звонков, где заголовок несёт тип звонка. Две строки никогда не дублируют друг
друга.

Приоритеты зарезервированы, а не декоративны: **пропущенный** звонок — это
`urgent`, потому что на юните без оператора именно ради него и стоит
прерываться.

Теги — обычные слова, и это проверено, а не предполагается: ntfy заменяет
распознанный шорткод эмодзи картинкой, и тогда теряется слово, по которому
работает фильтр. Ни один из семи тегов ниже не является алиасом в
[github/gemoji](https://github.com/github/gemoji), по которому ntfy и
разрешает шорткоды, — а вот `phone`, `telephone`, `envelope` и `bell`,
очевидные имена для такого релея, являются.

| Событие | Теги |
| --- | --- |
| SMS | `rackphone,sms` |
| Входящий звонок | `rackphone,call,incoming` |
| Пропущенный звонок | `rackphone,call,missed` |
| Отклонённый / заблокированный | `rackphone,call,rejected` / `,blocked` |

## Приватность

Это выкачивает содержимое сообщений с телефона в базу на хосте и дальше в ntfy.
Три средства контроля:

- `include_body=0` — хост узнаёт, что сообщение пришло, от кого и когда, при
  этом содержимое не покидает устройство.
- Только входящие — отправленные сообщения и исходящие звонки не читаются
  никогда.
- Метрики несут **только счётчики**. Ни номеров, ни тел; метка метрики по своей
  природе имеет неограниченную кардинальность, а Prometheus — неподходящее
  хранилище для содержимого.

Зеркалирование уведомлений приложений намеренно не реализовано. Оно копировало бы
с устройства произвольное стороннее содержимое без всякой пользы для того, чем
этот проект занимается.

Топик ntfy — общий секрет, а не контроль доступа. Любой, кто знает имя топика,
может его читать, если сервер не требует аутентификации на чтение.
